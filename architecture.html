Deadlock攻略サイト アーキテクチャ

最終更新: 2026-09-05 (ゲーム本体から公式日本語ローカライズと画像393件を取得。日本語化方針を改訂)

このファイルはClaude Codeがセッション開始時に読む前提の要約ドキュメント。装飾なし・軽量を維持すること。

目的

  • 解説・考察記事は作らない。データベース型の日本語リファレンス＋ビルドツールに徹する
  • ヒーロー・アイテム・スキル・オブジェクトの生データを日本語で閲覧できる
  • ビルドを組んで、実数値・成長曲線(Weapon/Vitality/Spirit)を可視化できる
  • ビルドをURLで共有できる(アカウント不要)
  • ゲームデータの変更をGameTracking-Deadlockの差分から検知し、DBと変更履歴を更新する

データソース

  • GameTracking-Deadlock (https://github.com/SteamTracking/GameTracking-Deadlock) ― 唯一のデータソース。ゲームの生データ(VData/protobuf/ローカライズ文字列)。 ヒーロー・アイテム・スキル・オブジェクトの数値、日本語文字列はすべてここから抽出する。
  • deadlock.wiki ― 参照可(2026-09-04にルール変更)。 ゲームの計算式・仕様がデータ側に無いため、計算式の確認とパース結果の検算に使ってよい。 ただし本文・訳文の転載は引き続き不可。 参照して判明した仕様は、このファイルに自分たちの言葉で記録すること。

サイト構成: 完全静的

ビルド共有はURLエンコード方式(ヒーローID・アイテムIDをURLのクエリ/ハッシュに埋め込み、読み込み時にJSで復元)にするため、 サーバー・データベースは不要。静的ホスティング(GitHub Pages等)のみで完結する。

重要: IDはゲーム内部の実ID(VData上のID)をそのまま使うこと。配列の連番などを使うと、 アイテム追加・削除のたびに既存の共有URLが別のビルドを指してしまい壊れる。

技術スタック(確定)

  • サイト: Astro + TypeScript ― ヒーロー/アイテム/スキル一覧・詳細ページは data/*.json からビルド時に静的生成する。 デフォルトでJS 0KB配信。ビルドツール(ビルド作成・成長曲線・URLエンコード/デコード)のみを クライアントサイドの島(client:load)として埋め込む。
  • パーサー: Node.js + TypeScript ― サイトと言語を統一する。data/*.json の型定義をパーサーとフロントエンドで共有し、 パース側の構造変更がビルドエラーとして検出されるようにする。 GitHub ActionsのセットアップもNodeだけで済む。
  • グラフ描画: 自前SVG(ライブラリ非依存) ― 描くのは点が数十個の区分線形グラフのみ。SVGを直接生成し、 軸ラベル・ツールチップ・ダークモード・日本語表記を完全に制御する。
  • 更新検知: GitHub Actions の cron ― 1日1回、GameTracking-Deadlockの最新コミットSHAを取得し、前回記録と比較。 差分があれば変更ファイルのみ再パース → data/*.json を更新 → changelogを生成 → 自動コミット → GitHub Pagesへデプロイ、までを無人で回す。 前回SHAはリポジトリ内の状態ファイル(data/.upstream-sha)に保持する。
  • ホスティング: GitHub Pages (github.io サブドメイン) ― リポジトリと一体で、更新検知のActionsからそのままデプロイできる。 独自ドメインは後からCNAMEで追加可能なので、当面は無料サブドメインで運用する。

データパイプライン

  1. 初回一括抽出: 現時点のGameTracking-Deadlockから全ヒーロー/全アイテム/全スキル/全オブジェクトをパースし、 heroes.json / items.json / abilities.json / objects.json を生成する(実IDをキーにする)
  2. 継続更新: 新規コミットを検知したら、変更のあったファイルのみ再パースしてJSONを差分更新する
  3. 変更履歴: 更新前後のJSONを比較して構造化された変更点(数値差分)を自動算出し、changelog的な形で保持する (生VDataの差分ではなく、パース後JSON同士の差分の方が正確で扱いやすい)

成長曲線 / ビルドシミュレーター(仕様確定)

単純なレベル別ステータス表ではなく、ビルドオーダーに沿った実数値の軌跡を描く。 SHOPでアイテムを1個ずつ購入していく過程で、各時点の実ステータスを算出してプロットする。

計算に含めるもの

  1. ヒーロー基礎ステータス
  2. 各アイテムの基礎上昇ステータス
  3. アイテムTYPE(Weapon / Vitality / Spirit)ごとの累積上昇ステータス
  4. レベルアップボーナス

軸とレベルの扱い

  • 横軸 = 購入順(0個目=素の状態、1個目、2個目 …)。ステップ状の区分線形で結ぶ。
  • レベルは累積ソウルから自動算出する。 各購入時点の累積コストをその時点の獲得ソウル総額とみなし、レベルを求めてボーナスを加算する。 ユーザーはアイテムを選ぶだけでよい。
  • 横軸ラベルには 3個目 / 累積4,750ソウル / Lv8 のように 購入順・累積ソウル・レベルを併記し、購入順軸とソウル依存レベルの対応関係が読み取れるようにする。

縦軸

  • 素ステータスのみを扱う(HP、武器ダメージ、スピリットパワー、移動速度 等)。 DPSや実効HPのような推計・派生指標は出さない。データベース型サイトの方針を優先する。
  • 表示する系列はユーザーが選択できる(チェックボックス等で複数系列の重ね描き)。

条件付き効果

  • グラフに乗せるのは常時発動のパッシブのみ。
  • 発動中のみ・スタック時・アクティブ使用中などの条件付き効果はグラフには加算しない。 アイテム詳細にテキストとして表示するに留める。

パーサーが解決しなければならない継承

  • _include ― abilities.vdata はヒーロー別の .vdata_inc を読み込む形だが、 リポジトリ上のファイルには実体が展開済みで入っている
  • _multibase ― 例: _multibase = [ "weapon_upgrade_t1" ]。アイテムはティア共通の基底を継承する
  • hero_base ― 各ヒーローは hero_base を土台に差分を持つ

ビルドシミュレーターの計算に使うキー

  • 常時パッシブの判定: m_AutoIntrinsicModifiers[].m_vecAutoRegisterModifierValueFromAbilityPropertyName に列挙されたプロパティが、装備するだけで常時乗る値。ここに載らない値は条件付きなのでグラフに加算しない。
  • 加算値の実体: m_mapAbilityProperties.<プロパティ名>.m_strValue
  • 合算キー: 同じプロパティの m_eProvidedPropertyType (例 MODIFIER_VALUE_AMMO_CLIP_SIZE_PERCENT)。 これはレベルアップボーナス m_mapStandardLevelUpUpgrades のキーと同じ名前空間なので、 ヒーロー基礎値・アイテム・レベルボーナスを同一キーで足し合わせられる。
  • 縦軸の選択肢: m_eDisplayType(例 EClipSizeIncrease)。 heroes.vdata の m_ShopStatDisplay.m_eWeaponStatsDisplay / ...m_vecDisplayStats が Weapon/Vitality/Spirit ごとの表示ステータス一覧なので、これをそのまま縦軸のチェックボックスに使う。
  • アイテムTYPE: m_eItemSlotType = EItemSlotType_WeaponMod(97件) / EItemSlotType_Armor(93件) / EItemSlotType_Tech(85件)
  • TYPEごとの累積上昇ステータス: heroes.vdata の m_MapModCostBonuses。 そのカテゴリに使った累計ソウル額に応じて nGoldThreshold → flBonus の階段関数でボーナスが決まる。 アイテムの個数・種類・ティアは無関係。全ヒーローで同一のテーブル。 値は「ステータス計算式」の項に掲載(2026-09-05 実測で全33値の一致を確認済み)。
    【訂正 2026-09-05】ここには当初 m_mapPurchaseBonuses(ティア別 T1〜T5、Armorなら 7/8/9/10/11)を 「アイテムを1個買うたびにティアに応じて加算される」ものとして載せていたが、 実測の結果いずれの値とも一致せず、誤りと判明した。 正しいフィールドは m_MapModCostBonuses。 m_mapPurchaseBonuses が何を制御しているのかは未調査。
  • ヒーロー基礎ステータス: m_mapStartingStats。 キーは E* 形式(EMaxHealth, EMaxMoveSpeed, ELightMeleeDamage 等)で、 アイテム/レベルボーナスの MODIFIER_VALUE_* とは別の名前空間。 両者の対応表(どのMODIFIER_VALUEがどの基礎ステータスに、加算か乗算かで効くか)は データ上に無いので、こちらで定義する必要がある。ここがシミュレーターの残りの山。
  • 枠制限: heroes.vdata の m_mapItemSlotInfo.<TYPE>.m_arMaxPurchasesForTier = [ 6, 6, 6 ]
  • 継承: 各ヒーローは _base = "hero_base" を持つ。 レベルアップボーナスはヒーローごとに違う(例: hero_base の BASE_HEALTH_FROM_LEVEL は 62 だが hero_inferno は 39)ので、継承解決を省略すると数値が狂う。

ローカライズの所在(2026-09-05 訂正)

GameTracking-Deadlock に入っているのは english のみ。japanese を含むパスは1件も無い。 当初はこれを根拠に「日本語は自前で翻訳するしかない」と判断していたが、これは誤りだった。

ゲーム本体には公式の日本語ローカライズが同梱されている。 <Deadlockインストール先>/game/citadel/resource/localization/<group>/<group>_japanese.txt に実訳が入っている(スタブではない)。2026-09-05 にゲーミングPCから取得し、 game-localization/ に置いた。形式は english と同一なので同じパーサーがそのまま読む。

取得時の検証: ゲーム本体側の english 10,616トークンは、GameTracking由来の data/localization.english.json と全件ハッシュ一致した。 同じ内容バージョンなので、日本語訳はトークンIDでそのまま噛み合う。

さらに、末尾 _search のトークンにひらがな・ローマ字の読みが入っている (例: 「基礎拡張マガジン きそかくちょうまがじん kisokakuchoumagajin extended magazine」)。 現在のパーサーは _search を除外しているが、日英どちらでもヒットさせる検索を作るときは ここが使える。検討事項として残す。

日本語化の方針(2026-09-05 改訂)

公式訳の取り込みを主とし、自前翻訳は公式に無い分の補完に限る。 当初の「すべてこちらで翻訳して保持する」方針は、公式訳の存在確認により不要になった。 10,616トークン中 10,550件(99.4%)に公式訳がある。 数値データは英語版と同一なので、翻訳が関わるのは表示テキストのみ。

表記ルール

  • 名称は日本語を主、英語を併記する。 ヒーロー名・アイテム名・スキル名は見出しを日本語にし、英語名を副として並べる (例: 見出し「拡張マガジン」/ 副「Extended Magazine」)。 ゲーム本体が英語表示のため、ショップ画面と照合できるよう英語名は必ず残す。
  • 検索は日英どちらでもヒットさせる。検索インデックスに日本語名・英語名の両方を入れる。
  • 説明文・ステータス名・UI文言はすべて翻訳する(アイテム277件、スキル約360件)。

対訳辞書

  • 置き場所: data/i18n/ja.json。キーはローカライズファイルのトークンID (例 upgrade_clip_size, upgrade_ammo_scavenger_desc)。
  • 各エントリは 日本語訳 と 翻訳時点の英語原文のハッシュ を持つ。 ハッシュは localization.english.json の hash と同じ値(sha1 先頭12桁)をそのまま持つ。
  • 更新時、英語原文のハッシュが変わったトークンを「要再翻訳」として自動検出し、 changelogに含める。文言変更を取りこぼさないための仕組み。
  • 未訳・要再翻訳のトークンは英語原文をそのまま表示(フォールバック)し、 未訳であることが分かる表示にする。翻訳が追いつかなくてもサイトは常に成立する。

未訳の66件

公式訳が無いのは66件。ほぼすべてが DPS_prefix StaminaRestore_postfix のような 単位の接頭・接尾辞で、文章ではない。ここだけ自前で埋める。 内訳は citadel_attributes 32 / citadel_main 21 / citadel_heroes 9 / citadel_mods 4。 data/i18n/ja.json 側で needsTranslation: true と英語原文 en を持たせてある。

翻訳とライセンス上の注意

公式訳はValveの著作物なので、サイトに載せるのはゲーム内表記との一致が目的であることを明確にする。 自前で補う66件については、Valveの英文をそのまま転載するのではなく、データの意味を日本語で記述する形をとる。 deadlock.wiki の日本語訳を参照・流用しない(検算は数値のみ)。

ステータス計算式(2026-09-05 実測確定)

deadlock.wiki を参照して整理した内容を、2026-09-05 にゲーム内で実測して検証した。 ステータスごとに%の合成規則が違うという前提は正しかったが、 購入ボーナスの仕組みについては当初の理解が根本的に誤っており、実測で判明して修正した (下記「購入ボーナス」の項)。

実測はすべて Inferno / サンドボックス / レベル1 で行った。 記録は 実測チェックリスト_記入済み.md。

購入ボーナス ― カテゴリ別の累計投資額テーブル(重要な訂正)

当初「アイテムを1個買うたびに、そのTYPEとティアに応じた固定ボーナスが付く」と書いていたが、 これは誤りだった。実際はそのカテゴリに使った累計ソウル額だけでボーナスが決まり、 アイテムの個数・種類・ティアは無関係。

参照すべきフィールドも違った。正しくは heroes.vdata の m_MapModCostBonuses (nGoldThreshold → flBonus の表)。 我々が使っていた m_mapPurchaseBonuses(ティア別 T1〜T5)は、実測値のどれとも一致しない。

最大HP ― %は加算合成

最大HP = (基礎HP + Boon数 × Boonあたりのボーナス) × (1 + Vitality系%の合計) + 平坦ボーナスHP
  • Vitality系の%は互いに加算してから1回だけ掛ける。+10%が2つなら ×1.20(×1.21ではない)
  • 平坦ボーナスHPは%倍率がかかった後に足すので、%の恩恵を受けない
  • データとの対応: 「Boonあたりのボーナス」= MODIFIER_VALUE_BASE_HEALTH_FROM_LEVEL、 「Boon数」= MODIFIER_VALUE_BOON_COUNT(標準レベルアップごとに1)。 hero_base は 62、hero_inferno は 39 とヒーローで異なる
  • 実測で確認できた部分: 平坦ボーナスHPが%倍率の後に足されること。 830 × 1.15 + 210 = 1164.5 に対し実測 1164。 %が掛かるのは基礎HPであって、平坦加算後の値ではない。
  • 実測で確認できていない部分: 実測はすべてレベル1(Boon数0)で行ったため、 Boon分が%倍率の内側に入るのか外側なのかは検証できていない。 式の (基礎HP + Boon分) × という括りは deadlock.wiki の記述のままで、実測の裏付けは無い。
  • 同じく未検証: 「Vitality系%は互いに加算」という規則。 実測時に効いていた%は投資額テーブル由来の1つだけで、複数の%が同時に掛かる状況を作っていない。

武器ダメージ ― %は乗算合成

最終ダメージ = (基礎ダメージ × ダメージ倍率) + 平坦ボーナス
               × 距離減衰 × 耐性 × クリティカル倍率
  • %は互いに乗算して1つの倍率にまとめる。HPとは規則が逆なので要注意
  • 平坦ボーナスは%倍率の後に加算。ただし距離減衰・耐性・クリティカルの影響は受ける
  • 成長曲線に出すのは「距離減衰・耐性・クリティカル」を除いた素の値まで(方針どおり対戦前提の値は出さない)
  • 実測で確認できた部分: 武器投資額のボーナスは%であって平坦値ではない。 武器ダメージを持たない Rapid Rounds(連射速度+9%のみ)を1個買っただけで、 ステータスパネルに「9% 武器ダメージ」の行が新たに現れ、 1発ダメージ 5.5 の表示が 6 に変わった(5.5 × 1.09 = 5.995)。
  • 未検証: 「%は互いに乗算」という規則。実測では%が1つしか効いていない。

スピリットパワー ― 平坦は加算、%は乗算

スピリットダメージ = 基礎ダメージ + (スピリットパワー × 各スキルの係数)
  • 各所からの平坦スピリットパワーはすべて加算されて1つの値になる
  • スピリットパワーの%増加は互いに乗算し、合計値に対してかかる
  • スキルへの反映は線形。係数はスキルごとに異なる(小さいもので×0.019、大きいもので×0.8程度)
  • データとの対応: レベルアップの MODIFIER_VALUE_TECH_POWER = 1.1 が 「Boonあたり+1.1スピリットパワー」に一致した。パース結果の裏付けが取れている
  • 実測で確認できた部分: レベル1→4でスピリットパワーが 0 → 1.1 → 2.2 → 3.3 と1レベルあたり +1.1 で推移。データの値と完全一致。 Tech投資額のボーナスも平坦加算で確定(投資800で +7)。
  • 未検証: 「%は互いに乗算」という規則。スピリットパワーの%増加を持つ状況を作っていない。

実測結果(2026-09-05)

  1. 「Boon」の定義 ― 確定。標準レベルアップ1回 = Boon 1。
    アイテム0個でレベルだけを 1→2→3→4 と上げたところ、 最大HP 830 / 869 / 908 / 947(1レベルあたり +39)、 スピリットパワー 0 / 1.1 / 2.2 / 3.3(1レベルあたり +1.1)。 hero_inferno の BASE_HEALTH_FROM_LEVEL = 39 / TECH_POWER = 1.1 と全区間で完全一致した。 アイテム購入側は Boon とは別系統(投資額テーブル)であることも判明した。
  2. Armorの購入ボーナスは最大HPに効く ― ただし仕組みが想定と違った。
    HPを一切持たない Armor アイテムを買っただけで 830 → 905 → 930 と増加したので、 購入ボーナスがHPに効くこと自体は確認できた。 しかし値はティア別の固定%(+7%)ではなく、累計投資額由来(+9% → +12%)だった。 参照フィールドが m_mapPurchaseBonuses ではなく m_MapModCostBonuses であることが判明。詳細は上記「購入ボーナス」の項。
  3. WeaponMod のボーナスは%。平坦値ではない ― 確定。
    武器ダメージを持たない Rapid Rounds を1個買うと ステータスパネルに「9% 武器ダメージ」が現れ、1発ダメージ 5.5 → 6 に変化。 MODIFIER_VALUE_WEAPON_DAMAGE_INCREASE は単位情報を持たないが、 %として扱うのが正しい。投資額800で +9%(データ値と一致)。
  4. Tech のボーナスは平坦スピリットパワー加算 ― 確定。ただし値は +4 ではなく +7。
    スピリットパワーを持たない Mystic Expansion を1個買うと 0 → 7。 平坦加算であることは想定どおりだったが、+4 という予測値は 誤ったフィールド(m_mapPurchaseBonuses)を見ていたことによるもので、 正しい m_MapModCostBonuses の投資額800の値 +7 と一致した。

実測しても確定できなかったこと

  • Boon分が%倍率の内側か外側か。 実測はすべてレベル1(Boon数0)で行ったため、 (基礎HP + Boon分) × (1 + %) なのか 基礎HP × (1 + %) + Boon分 なのかを区別できていない。 足りなかったもの: レベルを上げた状態でArmorアイテムを買う測定。 例えばLv4(Boon 3回 = +117)で投資800なら、 前者は (830+117)×1.09 = 1032.2、後者は 830×1.09+117 = 1021.7 と10以上ずれるので判別できる。
  • 複数の%が同時に効くときの合成規則(加算か乗算か)。 HP・武器・スピリットのいずれも、実測時に効いていた%は投資額テーブル由来の1つだけだった。 足りなかったもの: %ボーナスを自前で持つアイテム(例: 最大HP+%を持つArmor)を 投資額ボーナスと重ねて買う測定。
  • 投資額テーブルの 3,200 → 4,800 の跳躍(★行)の意味。 データには flPercentOnGraph という別系列の値が併記されているが、 これが何を制御しているかは未調査。ゲーム内UIで★が付く行と対応している可能性がある。 足りなかったもの: 高額投資での追加測定と、UI側(panorama)の実装確認。

アイコンの扱い

src/components/ItemIcon.astro が public/images/ に実画像があればそれを、無ければ同じ寸法の プレースホルダを描く。判定はビルド時に行う。 ゲーム本体から画像を抽出してファイルを置くだけで全ページが実画像に切り替わり、 呼び出し側の変更は不要。

プレースホルダはTYPE色の枠・ティア表記(I/II/III/IV)・ACTIVE/IMBUEバッジを 本番と同じ位置に持つので、画像が入ってもレイアウトが動かない。

IMBUEの判定(追加調査)

参考画像にあった IMBUE バッジの根拠がデータに見当たらなかったが、 m_TargetAbilityEffectsToApply が CITADEL_TARGET_ABILITY_BEHAVIOR_IMBUE_* のものがそれだった。 items.json に isImbue として追加。該当は9件 (Mystic Expansion / Mystic Reverb / Compress Cooldown / Echo Shard / Duration Extender / Surge of Power / Quicksilver Reload / Mercurial Magnum / Ballistic Enchantment)。

ステータス表示の但し書き

合計ステータスは常時パッシブを単純加算した値までで止めている。 %の合成規則(加算か乗算か)と基礎ステータスへの反映は実測待ちのため、 最終値には変換していない。画面上にもその旨を明示している。 実測が済み次第、ここを実数値と成長曲線に置き換える。

ラベル解決の注意

MODIFIER_VALUE_* に読めるラベルを与える際、同じキーを複数のプロパティ名が使うため、 最初に見つけた名前を採ると特殊な用途の名前を拾ってしまう (TECH_POWER に対して「チャージアビリティのボーナススピリットパワー」など)。 出現回数が最も多い名前を選ぶようにしてある(同数ならラベルが短い方)。

2026-09-05 に src/lib/data.ts の modifierLabel() へ集約し、 次の順で引くようにした。ページごとに同じ処理を持たない。

  1. アイテムのプロパティ名からの投票。対象が最も広く、条件付きも区別できる。 ラベルが衝突するもの(武器ダメージ / 近距離 / 遠距離)は、ゲーム側の <名前>_conditional(「（範囲内）」など)を後ろに足す。 ラベルに条件語が既に入っている場合は足さない (「対NPC武器ダメージ対NPC」になるため)。
  2. ローカライズが直接持っている <キー>_label。 日本語辞書には243件ある。ただし投票より対象が狭く、 投票で拾える49種のうち直接引けるのは33種しかない。
  3. レベル成長にしか使われない4キー (BASE_HEALTH_FROM_LEVEL / BASE_BULLET_DAMAGE_FROM_LEVEL / BASE_MELEE_DAMAGE_FROM_LEVEL / BOON_COUNT)は ショップアイテムが供給せず、ゲームのローカライズにも文字列が無い。 表示のためにこちらで名前を与えているもので、ゲーム内表記ではない。

説明文のプレースホルダ解決

Valveの説明文には差し込み記法が埋まっている。そのまま出すと 「{s:NonHeroHealPct}% effective」のように壊れて見えるため、describe() で解決する。

  • {s:プロパティ名} → そのアイテム/スキル自身のプロパティ値
  • {g:citadel_inline_attribute:'X'} → 文中に埋め込むステータス名。 引き先は InlineAttribute_X。 ステータス行の見出しに使う X_label とは別トークンで、訳も違う (BonusFireRate: 「ボーナス発射速度」/「発射速度」)。 説明文中に現れる33種のうち21種は InlineAttribute_ にしか無く、 X_label を引いていた頃はスキル説明に英単語が残っていた。 SpiritIcon だけは文字ではなくアイコンの差し込み位置なので除去する。
  • {g:citadel_binding:'X'} → キーバインド。[前進] のように括って示す
  • 解決できないものは読める形に整えて残す(空欄にすると文意が壊れるため)
